## 1. 概要

> **お題に対して、一人ひとりが20分で自分の提案を練り上げる。
> できた提案を会議室の壁に並べ、それを見ながら人どうしで話し合う。**

### 特徴

1. 参加者が**非同期で**、お題に対する自分の意見を練り上げて提示する
2. **AIメンバー**が擬似的なグループディスカッションに加わり、参加者の考えを広げる
3. 20分の打ち込みが終わると、各参加者が**自分の提案スライド**を手にし、それが**会議室の壁**に貼り出される
4. 壁の上では、マッピングやタグによって、**似ている提案・対極にある提案**が見えるようになっている
5. 参加者は壁に貼られた提案を見ながら、**人どうしで**話し合う

### 製品が受け持つ範囲

| | 製品の中 | 製品の外 |
|---|---|---|
| 内容 | 20分の打ち込み、提案スライドの作成、壁への掲示と可視化 | 人どうしの議論 |
| 課金 | 対象 | 対象外 |

製品が責任を持つのは「**各自の提案がしっかりしているか**」まで。会議の結論そのものには責任を持たない。

## 2. なぜこの構造にしたか

### 2.1 解こうとしている問題

マンション管理組合やPTAなどの会合では、準備がないまま全員が集まり、その場で議論が始まる。

> **一人ひとりの意見がまとまっていない段階で人どうしを議論させると、力関係が生まれ、自分の意見を言えない人が出る。**

v1は「場で飛び交う発言から論点を整理する」設計だった。しかし、場で出る発言そのものが力関係で歪んでいるなら、それをいくら上手に整理しても、歪んだ材料を整理するだけになる。

### 2.2 打ち手

順番を入れ替える。

```
【v1】集まる → その場で意見を出し合う → 論点を整理する → 議論する
【v2】一人ずつ、自分の意見を最後まで作り切る → 並べて見る → 議論する
```

- 意見を作る段階では、**人の相手をしない**（相手はAIだけ）。だから力関係が生まれない
- それでも一人で考えるだけにならないよう、**AIメンバーが別の視点をぶつける**
- 作り切った意見なら、名前を出して人前に出しても怖くない

## 3. 考え方：ダブルダイヤモンド

デザイン思考のダブルダイヤモンドを、一人ひとりの思考の型として使う。

```
         正しい問題を見つける            正しい解決を見つける
            発散      収束              発散      収束
    ●  ─── 探索 ─── 定義 ───  ●  ─── 展開 ─── 提供 ───  ●
 対象領域                     課題                      解決策
```

この図で押さえておくことは次のとおり。

- **正しい問題を見つけること（左のダイヤ）が、抜け落ちやすい**
- その中から、解決すべき課題を決める
- その課題に対して、アイディアを広げていく
- ただし、アイディアを広げていくうちに、**何が問題だったのかを考え直すために左側へ戻ってくる**
- 左右を**行き来するうちに、課題と解決策が組になって見えてくる**
- 最終的に、**黄色の3点（対象領域・課題・解決策）を一つのストーリーとして語れる**ようになる

**これが、参加者一人ひとりが20分で目指すこと。**

> 補足：管理組合やPTAの議題は「共用自転車を廃止するか」のように、**解決策の形で持ち込まれる**ことが多い。課題が決まっていないまま解決策を話し合うので、噛み合わなくなる。「高齢者の安全が」という発言は、論点がズレたのではなく、左のダイヤに戻ろうとしていると読める。

> 参照：https://note.com/whgc_official/n/n48a2a5cf27c7 （図のみ参照。本文は環境のネットワーク制限で未読）

## 4. 利用の流れ

```
ホスト        お題と背景を登録する（投影スライドとして取り込む）
                │
                ▼
参加者        それぞれのタイミングで20分の打ち込みを行う
（非同期）     ・会議の冒頭でやるか、事前にやってもらうかはホストが決める
                │
                ▼
壁            提出された提案スライドが貼り出される
                ・似ている提案／対極にある提案が見える
                ・時間制限なしで閲覧できる。一定期間後に自動で削除
                │
                ▼
会議          壁を見ながら、人どうしで話し合う（製品の外）
```

### 4.1 ホストが選べる2つのやり方

| | 会議の冒頭でやる | 事前にやってもらう |
|---|---|---|
| 向いている場 | 準備してこないことがわかっている会合 | 準備をしてもらえる会合 |
| 会議の時間 | 最初の20分を打ち込みに使う | 会議の時間を全部、議論に使える |
| 注意 | **同じ部屋で音声入力をすると周りに聞こえる** | やらずに来る人が出る。その場合は冒頭でやってもらえばよい |

どちらを選んでも、遅れて来た人は着いた時点から自分の20分を始めればよく、**他の人の進行は止まらない**。

## 5. 20分の流れ（10工程）

| # | 工程 | ダイヤ | 相手 | 中身 | 成果 |
|---|---|---|---|---|---|
| 1 | お題の提示 | — | — | ホストが用意した、お題と背景のスライドを見る | **● 対象領域** |
| 2 | 拡散 | 左・発散 | AIファシリテーター（1対1） | 自分の意見や経験を入力する（タイピングまたは音声）。AIが掘り下げたり、広げたりする | |
| 3 | 俯瞰 | 左・頂点 | — | みんなの声を整理したものを見る（課題の候補／解決アイディアの候補／主な論点＝対立点と合意点） | |
| 4 | 収束 | 左・収束 | 本人＋AIメンバー3人＋AIファシリテーターの5人 | 自分は何を課題と考えるかを決める。ソクラテス式の問答、または grill me（容赦なく問い詰める）形式で詰める | |
| 5 | 課題設定 | 左・終点 | 同上 | 課題を言葉として書き表す | **● 課題** |
| 6 | 発散 | 右・発散 | 同上 | 課題に対するアイディアをどんどん出す。途中でAIメンバーが「そもそも課題は合っているのか」と**ちゃぶ台を返す** | |
| 7 | 往復 | 左右 | 同上 | 課題と解決アイディアを組にして議論する | |
| 8 | 収束 | 右・収束 | 同上 | 時間切れが近づく中で、アイディアを決め、課題を調整し、お題・対象領域を書き表す | **● 解決策** |
| 9 | ストーリー化 | — | 編集者AI | 決まった3点を一つのストーリーとして文章にする。本人がコメントして確定する | |
| 10 | スライド化 | — | — | 確定した内容を1枚のスライドにまとめる。提出したら完了 | **提案スライド** |

### 5.1 時間配分の叩き台（すべて感覚値）

| 工程 | 分 | 削れるか |
|---|---|---|
| 1 お題 | （20分の外、または冒頭の1分） | — |
| 2 拡散 | 5 | **削りにくい**（本人の入力速度で決まる） |
| 3 俯瞰 | 1 | |
| 4〜5 課題を決める | 4 | |
| 6〜8 アイディアと往復 | 6 | **しわ寄せがここに来る** |
| 9 ストーリーの確認 | 3 | **削りにくい**（本人が読んで直す時間） |
| 10 スライド化・提出 | 1 | |
| **計** | **20** | |

**懸念：** 一番大事な「行ったり来たり」（工程6〜8）が、最も時間を削られやすい位置にある。

### 5.2 時間の扱い

- 時計で区切るのか、工程の完了で進むのかは未決（第11章）
- 工程8は「時間切れが近づく中で収束させる」とあるので、**残り時間を把握して進行を寄せる**必要がある。工程4〜8では**AIファシリテーターがこれを受け持つ**（6.1）

## 6. AIの役割

| 役割 | 登場する工程 | 仕事 |
|---|---|---|
| **ファシリテーター** | 2、4〜8 | 工程2：本人の意見・経験を掘り下げる、広げる。工程4〜8：グループディスカッションを進行する（下記） |
| **集約**（人格なし） | 3 | 他の参加者の声を集めて、課題候補・アイディア候補・論点を整理する |
| **メンバー3人** | 4〜8 | 本人・ファシリテーターと5人でディスカッションする。問い詰める、別の視点を出す、ちゃぶ台を返す |
| **編集者** | 9〜10 | 3点をストーリーの文章にし、スライドにまとめる |

### 6.1 グループディスカッションでのファシリテーターの仕事

工程4〜8は、**本人＋AIメンバー3人＋AIファシリテーター1人の5人**で行う。メンバー3人だけだと、誰が話すか、いつ次の工程へ進むかを決める人がいない。ファシリテーターがそれを受け持つ。

- **発言の順番を決める。** 次に話すAIメンバーを1人指名する（6.3の「一度に話すAIは1人」を守る役）
- **時間を管理する。** 残り時間を見て、拡散から収束へ、課題設定から右のダイヤへと進行を寄せる（5.2）
- **工程の切り替えを宣言する。** 「ここで課題を言葉にしましょう」「いったん課題に戻りましょう」など
- **本人が置いていかれないようにする。** AIメンバーの議論が先走ったら止め、本人に話を戻す
- 自分の意見は出さない。課題も解決策も、決めるのは本人

### 6.2 メンバー3人の立場（叩き台・未決）

3人が同じことを言っても意味がないので、立場を分ける。例：

| | 例A | 例B |
|---|---|---|
| メンバー1 | 当事者に寄り添う人 | 現実派（予算・手間・前例） |
| メンバー2 | 反対の立場の人 | 理想派（そもそもどうあるべきか） |
| メンバー3 | 外から来た人（素朴な疑問） | 懐疑派（本当にそれが課題か） |

### 6.3 AIの発言のルール

AIは人が読むより速く文章を出す。3人が一斉に話すと、参加者は読み切れなくなる。

- **一度に話すAIは1人**（ファシリテーターが指名する）
- **1回の発言は2〜3行まで**
- **発言は問いで終える**（本人に考えさせる）
- **結論を代わりに決めない**。課題も解決策も、決めるのは本人
- grill me 形式は強い。**問い詰めているのはAIで、見ているのは本人だけ**なので場の力関係は生まれないが、口調が強すぎると高齢の参加者が嫌になる恐れがある。強さを調整できるようにする

v1では「AIは決めない。今どこにいるかを言うだけ」とした。v2ではAIが個人に深く踏み込むが、**踏み込むのは本人しか見ていない対話の中**なので、v1でAIを控えめにした理由（全員の前でAIが判断すると角が立つ）は当てはまらない。結論を本人が決める点は変わらない。

## 7. 壁

### 7.1 掲示

- 提出された提案スライドが**ニックネーム付き**で貼り出される
- 名前は隠さない。ただし**本名かどうかは本人が選べる**（どこまで自分を出すかを、本人が決められる）
- **時間制限なしで閲覧できる。一定期間後に自動で削除される**

### 7.2 可視化

- **似ている提案**をまとめる
- **対極にある提案**を見えるようにする
- **タグ**で絞り込める

| 機能 | 流用できるもの |
|---|---|
| 似ている提案をまとめる | 広聴AI `llm_grouping`（LLMがグループを見つけて、各提案を振り分ける） |
| 対極にある提案を示す | いどばた `DebateAnalysis` の対立軸（axes） |

**ずれやすい点：** 似ている・対極を判定するのは「解決策」だけでよいのか、「課題」も見るのか。同じ解決策でも課題の捉え方が違う、という組が一番議論の価値があるはず（未決）。

## 8. 非同期にしたことで生まれる論点

### 8.1 工程3の「みんなの声」が、最初の人には少ない

非同期なので、**早く打ち込んだ人ほど、集まっている他の人の声が少ない状態で工程3を迎える**。1人目は誰の声も見られない。

選択肢（未決）：

| | やり方 | 弱み |
|---|---|---|
| a | その時点までに集まった声だけで作る。少なければ工程3を省く | 最初の数人は俯瞰ができない |
| b | AIが「想定される声」を作って補う（AIが作ったと明示する） | 実在しない声で課題を決めることになる |
| c | ホストがお題を登録するときに、背景資料から**課題の候補・論点の候補を先に作っておく** | ホストの見方に寄る |
| d | **c で始め、人が増えるにつれて実際の声で置き換えていく** | 実装が少し複雑 |

d が現実的と見る。

### 8.2 先にやった人の声が、後の人の考え方を方向づける

工程3の候補リストに先行者の声が入るので、**後からやる人は、先にやった人の枠組みで考えやすくなる**。形を変えた力関係になり得る。

ただし、工程2（自分の拡散）が工程3（俯瞰）より先にあるので、**自分の考えを出し切ってから他の人の声を見る**順番にはすでになっている。これがある程度の歯止めになる。

### 8.3 会議の冒頭でやる場合の音声入力

同じ部屋で全員が音声入力をすると、**周りに聞こえる**。「力関係なく本音を言える」という前提が崩れる。

→ 冒頭でやる場合はタイピングを勧める、イヤホンマイクを前提にする、など（未決）。

## 9. 技術構成

### 9.1 v1から楽になったこと

| | v1 | v2 |
|---|---|---|
| 部屋の音声を拾う | 必要 | **不要** |
| 話者の聞き分け | 課題だった | **問題にならない**（一人ひとりが自分の端末で入力する） |
| 会議中の全員の画面を更新し続ける | 必要（最大の技術リスク） | **不要** |
| 1人の不具合の影響 | 会議全体が止まる | **その人だけ**（セッションが独立している） |

### 9.2 流用できるもの

| 工程・機能 | 流用元 |
|---|---|
| 工程2 AIとの1対1の対話 | いどばた `chatController` / `themeChatRoutes` |
| 工程3 意見の構造化 | いどばた `extractionWorker` |
| 工程3・壁 似ているものをまとめる | 広聴AI `llm_grouping` |
| 工程3・壁 対立点・合意点 | いどばた `DebateAnalysis` |
| 壁の更新の配信 | Socket.IO（既存） |

### 9.3 新しく作るもの

- 10工程を順に進める**進行管理**（残り時間の把握を含む）
- AIの役割（ファシリテーター、メンバー3人、編集者）の**切り替え**と、ファシリテーターによる**発言順の指名**
- **提案スライドの生成**
- **壁**（掲示、マッピング、タグ、自動削除）
- 工程3の**集約のタイミング**（第8.1節）
- **決済**（人数による段階料金）

### 9.4 注意点

- **AIの利用枠が唯一の天井。** いどばたのAIは OpenAI の `gpt-5.6-luna` で、組織の利用枠は**1分あたり500リクエスト／50万トークン**（コミット `6ec5bf6` の記録）。OpenAIは出力上限として設定したトークン数を、呼び出した時点で枠から先取りする。見積もりでは、**同時に対話している人数で約40〜55人**が天井になる（決め手はトークン数）。いどばた本体の授業と同じ枠を共有している
- **天井の内側に収めるための設計（実装済み）：**
  1. AIが4人いても、**発言1回につき呼び出しは1回**（ファシリテーターが指名した1人の発言だけを作る）
  2. 工程3の「みんなの声」は**お題ごとに1回だけ作って全員で使い回す**
  3. 出力上限を小さく設定する（対話500、整理・ストーリー1,200、スライド800）
  4. 混んだときはエラーにせず**順番待ち**にする（会議室からの同時問い合わせは既定20まで）
  5. 会話を1回ごとに保存し、つなぎ直したら続きから再開できる
- **Railway・MongoDB・Vercel：** いずれも余裕がある。AIの返答を待つ時間がほとんどで、50人が同時に使ってもCPUは1コアの数％程度（見積もり）。MongoDBは50人で1分に約75回の書き込み。Vercelは画面のファイルを配るだけで、会議室の画面は開いたときだけ読み込む
  - v1で「Railway はプランの上限まで使い切っている」と書いたのは誤り。**上限の設定値**をプランの最大（8vCPU／8GB）にしてあるという意味で、実際の使用量の話ではなかった
  - バックエンドもMongoDBも**1台構成**。デプロイや障害で進行中の20分が切れる（再開はできる）。**会議が予定されている時間帯にはデプロイしない**
  - **Vercel は無料の Hobby プランで、非商用に限られる。課金を始める前に**、Vercel Pro・Railway・Cloudflare Pages などへ移す必要がある
- **置き場所：いどばた本体のバックエンドの中に作った。** v1で別アプリとしたのは、部屋の音声とリアルタイム更新が前提だったため。v2ではその理由がない
- **ライセンス：** 広聴AIは AGPL-3.0。**L1 では広聴AIのコードを使っていない**ので、まだ AGPL の条件は発生していない。壁のマッピングで `llm_grouping` を組み込む段階で発生する（v1で受け入れ済み）

## 10. ビジネスモデル

### 10.1 料金

| 参加人数 | 料金 | 1人あたり |
|---|---|---|
| 5人まで | 500円 | 100円 |
| 10人まで | 1,000円 | 100円 |
| 50人まで | 3,000円 | 60円 |
| 50人超 | 未定 | — |

- 課金の単位は**1回のお題（20分の打ち込み）**
- 壁の閲覧は時間制限なし。一定期間後に自動削除
- 500〜3,000円は、v1で整理した「**会議費として処理でき、誰も文句を言わない額**」に収まっている

### 10.2 原価（見積もり・未実測）

AIが4人いても発言1回につき呼び出しは1回なので、負荷はAIと1対1で話すのとほぼ同じになる。

| モデル | 1人あたり20分の原価（見積もり） |
|---|---|
| `gpt-5.6-luna`（いどばたの現在のモデル） | **約3〜6円**（会話の前半部分をキャッシュできるかで変わる） |
| Claude Sonnet 5（以前のモデル） | 約25〜55円（授業の実測で、lunaの約9倍） |

前提：やりとり30回（40秒に1回）、1回に送る量は平均5,500トークン、返答150トークン。

- 料金は1人60〜100円なので、**lunaなら十分に収まる**
- AIメンバーの問いかけの質を上げるために強いモデルへ切り替えると、**50人の枠（1人60円）は余裕がなくなる**
- v2の初版で「最上位のモデルだと収まらない可能性」と書いたのは、モデルが Anthropic だった前提での話。**実測で確かめる**ことは変わらない

**構造上の注意：** 人数が多い利用者ほど1人あたりの単価が下がり、**利幅が薄くなる**。

### 10.3 自動削除と保存の有料化（提案・未決）

v1では「論点を組織ごとに残し続ける台帳」を柱にしていた。v2は「一定期間後に自動削除」なので逆向き。

**提案：** 自動削除を標準にして、**残したい組織には保存を有料で提供する**。

- v1で決めた「100会議の後にサブスクを始める」と自然につながる
- 標準で消えるほうが、プライバシーの面で導入をためらわれにくい

### 10.4 v1から引き継ぐもの（要再確認）

- **営業をしない。** 参加者が自分の提案スライドを持ち帰り、それを見た人が次のホストになる流れで広がる。v2では**一人ひとりが成果物を持ち帰る**ので、v1より強い
- **再利用がなければ撤退。** 同じホストが2回目のお題を立てるかどうか

## 14. 実装の状況（L1：1人で20分を通しで試せる試作）

12.2 の L1 にあたる。L0（手で回す）は飛ばし、**実際に動く画面で20分と原価を測れる**ところまで作った。

### 14.1 できていること

| 層 | 内容 | 場所 |
|---|---|---|
| メニュー | ヘッダーに「いどばた会議室」 | `frontend/src/components/layout/Header.tsx` |

**進行のルール：**

- 工程2は参加者とファシリテーターの1対1。AIがメンバーを名乗っても、ファシリテーターとして扱う
- AIの判断で進められるのは工程7まで。工程5〜8は、課題（工程8では対象領域・課題・解決策の3点）がそろうまで進めない
- 工程8から先（3点の確定、ストーリーの確定、提出）は**参加者がボタンで決める**
- 参加者は、AIが書き留めた3点を自分の言葉に直せる
- 対象領域は、最初はお題をそのまま入れておき、工程8で書き直す
- お題の参加者がホストの選んだ人数（5／10／50人）に達したら、それ以上は参加できない

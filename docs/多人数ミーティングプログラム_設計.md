## 1. 位置づけ

いどばた（デジタル民主主義2030のOSS）の**同期版・小規模版**。

| | いどばた本体 | **本プログラム** |
|---|---|---|
| 同期性 | 非同期。各自が好きな時にAIと対話 | **同期。全員が同じ部屋に60分** |
| 規模 | 数百〜数万人 | **10〜20人** |
| 処理 | 日次バッチ（`dailyBatchProcessor`） | **リアルタイム（分〜秒）** |
| 目的 | 広く意見を集めて論点を抽出 | **その場の議論の論点を可視化する** |

## 2. 解く課題

### 2.1 対象の場

マンション管理組合の理事会・総会、PTAの会合、町内会、NPOの理事会、サークルの企画会議など。
**公式な会議と、非公式でカジュアルな会議の両方に適用できることを要件とする。**

### 2.2 前提条件（動かせない制約）

- 会議時間は**60分**と決まっている
- **開始は必ず遅れる**（実質50分）
- **事前の宿題は誰もやってこない**
- **アジェンダすら見ていない**

### 2.3 病理の構造

```
準備ゼロで全員が入場
  ↓
各自が「言いたいこと」を放出する（論点への接続なし）
  ↓
噛み合わない ＝ 誰の発言がどの論点に属するか、誰にも見えていない
  ↓
分岐①：時間切れ → 持ち越し（結論ゼロ、次回も同じ）
分岐②：司会が強引に決める → 結論は出る
        ただし「決定のコスト」を司会が“人格”で払う
        →「あいつは人の気持ちがわかっていない」
```

**分岐②が本丸。** 結論が出ないことが問題なのではなく、**結論と納得が両立しないこと**が問題。
そのツケを、無報酬のボランティア司会（理事長・PTA会長）が個人の評判で払っている。
だから翌年度、誰も司会を引き受けない。

### 2.4 論点のズレの類型

| | 型 | 例（共用自転車の件） | 扱い |
|---|---|---|---|
| ① | **派生** | 廃止の是非 → 高齢者の安全性 | 捨てず、別の箱へ |
| ② | **抽象度のズレ** | 駐輪場の運用 → 理事会の決め方そのもの | 上の階層に上げると終わらない |
| ③ | **事実と価値の混線** | 「何台あるか」と「高齢者に配慮すべきか」 | **分けないと絶対に決まらない** |
| ④ | **立場の表明を論点と誤認** | 「私は反対だ」「困る」 | 論点ではない |
| ⑤ | **すり替え** | 廃止の是非 → 「そんな話は聞いていない」 | 指摘の摩擦が最大 |

**③が最大の時間泥棒。** 事実確認で済む話と価値判断が同じ土俵で殴り合うと、60分は必ず溶ける。

## 3. 成功の定義

> **結論を出すことではない。論点を可視化すること。**

- 論点を混ぜない。**論点のズレを共通認識にする**
- **拡散は悪くない。** 持ち越しは失敗ではなく、設計された着地
- 価値観まで言語化されれば、良し悪しの争いではなく「**どの価値観を扱うか**」の選択になる

### 3.1 なぜ拡散を許すのか

「安全の話と秩序の話、その違いだね」と理解できれば、議論は復活する。
価値観が言語化されると、議論のレイヤーが一段上がる。

```
【従来】意見 vs 意見の対立
        「廃止すべき」 ⇔ 「残すべき」
        → 勝ち負け。負けた側に遺恨が残る

【価値観まで落ちた後】論点の「選択」
        秩序の話をするのか／生活の継続性の話をするのか
        → 良し悪しではない。どちらを今日扱うかの選択
        → 選ばれなかった方は、否定されたのではなく、まだ扱われていないだけ
```

普通の会議にもこのレイヤーは存在するが、**無自覚**である。誰も選んでいないのに、声の大きい人が論点を占領している。それを**明示的な選択に変える**ことが、本プログラムの本質。

### 3.2 【重要】検証されていない仮説

**「論点の違いが理解できれば議論が復活する」は仮説であり、実証されていない。**

逆の可能性がある。曖昧なまま喋っていたからこそ場が保たれていたケースで、
「あなたは秩序を、私は生活を大事にしている」と明示された瞬間、
**議論が復活するのではなく、対立が固定化する**かもしれない。
管理組合の人間関係は、会議が終わっても続く。

→ **Phase 0 の最重要検証項目のひとつ。**（第10章）

## 4. 製品の一行と、設計原則

> **「何の話をしているんだっけ？」を、代わりに言う。**

司会の技量のうち、再現が難しいのは「決める力」ではない。
**「今、論点がズレた」と気づき、角が立たない形で言語化する力**である。
決めるのは多数決でもできるが、これはできない。そして普通の人には無理。

### 設計原則

| | 原則 | 理由 |
|---|---|---|
| **P1** | **AIは決めない。現在地だけを言う** | 決定権を持たないから憎まれない |
| **P2** | **誰が言ったかは扱わない。何を議論すべきかだけを扱う** | 価値観を人格から切り離す |
| **P3** | **意見の多寡は見せない。論点の数だけ見せる** | 多寡が見えると少数論点が死ぬ |
| **P4** | **落選という概念を作らない** | 選ばれなかった論点は台帳に残る＝否定ではない |
| **P5** | **参加者に操作を要求しない**（投票のタップを除く） | 準備ゼロ・高齢者が前提 |
| **P6** | **主催者の会議後の宿題を減らす** | 主催者の犠牲こそが構造問題の核 |

### P2 の含意：話者分離を捨てる

**「誰が」を扱わない**と決めたことで、以下が同時に成立する。

| | 効果 |
|---|---|
| 技術リスク | マイク1本で15人を分離する難題が**消滅** |
| 参加者の操作 | **完全にゼロ**。スマホは純粋な出力装置 |
| 機微情報 | 「Aさんは苛立っている」が生まれない。**議事録に個人が紐づかない** |
| 原価 | 話者分離の処理が不要になり一段下がる |

**失うもの：** 発言量の偏り（「一人が60%喋っている」）が検出できない。

**代替：** 話者が分からなくても、同じ主張の反復は検出できる。

| | 言えること | 効果 |
|---|---|---|
| 話者あり | 「〇〇さん、さっきも同じことを」 | **人格攻撃**。司会が恨まれる構造そのもの |
| 話者なし | **「この論点は3回目です」** | **人を名指さずにループを止められる** |

ループしている本人は自分のことだと分かるが、公には誰も名指されない。面子が潰れない。

## 5. プログラム設計（60分）

### 5.1 時間配分

```
60分
 −10分  開始の遅れ（音声処理も不要）
 −10分  課題の共有 … 主催者が起点論点と背景を提示
 −10分  ラップアップ … 「決めること」「考えること」の仕分け
 ────
 30分  ← コア時間
```

**「課題共有の10分」は二重の役割を持つ。**
人間にとっては説明の時間、AIにとっては**初期材料の収集時間**（＋前回の論点台帳の読み込み）。
これによりコア30分の開始時点でAIは既に論点候補を持っており、**製品初動の空白が消える。**

### 5.2 コア30分のフロー

```
主催者が起点論点を提示（課題共有10分の中で）
    ↓
【拡散】参加者が意見を出す → 論点が広がる
    ↓
◆ 可視化① マインドマップ
    主催者＝放射状／参加者＝縦ツリー
    票数も意見数も見せない（P3）
    ↓
【投票】参加者がスマホで「どれから始めるか」を順位投票
    落選なし（P4）。順位だけ表示、票数は隠す（P3）
    ↓
【討論】1番目の論点を全員で議論
    ↓
◆ 可視化② 対立軸・合意点・相違点（DebateAnalysis相当）
    ↓
【ラップアップ】「決めること」「考えること」を仕分けて終了 → 台帳へ
```

### 5.3 区切り方

**時計では区切らない。** 会議は予定通り進まない。
区切りは**1回だけ**で、それは「投票」という人間の行為で起きる。

前半・後半という見通しは主催者に与えられるが、区切る時刻は固定しない。
**素人主催者に松葉杖を渡しつつ、会議の実際のリズムにも従う。**

### 5.4 【未決】30分の内訳

叩き台（**すべて感覚値。実測なし**）：

| | 分 | 根拠 |
|---|---|---|
| 拡散 | 12 | 15人が一言ずつでも10分は溶ける |
| 可視化① | 2 | マップを見て理解する時間 |
| 投票 | 3 | 15人のタップ。高齢者を含むと2分では終わらない |
| 討論 | 11 | 残り |
| 可視化② | 2 | 討論の中身の整理 |

**討論が11分しかないのが痛い。** 15人のうち5人しか喋れない。
削ると別のものが壊れる：

- 拡散を削る → 論点が出揃わず、可視化①の精度が落ちる
- 投票を削る → 代理入力が間に合わず、**正統性が崩れる**
- 可視化を削る → 見て理解する時間がなくなる

**逃げ道：** 2回目以降の会議では、前回の台帳のおかげで課題共有を10分→3分に圧縮できる。
討論が18分になる。**再利用されるほど良くなる**という設計と噛み合う。

→ **未決。拡散と討論のどちらを厚くするかを決める必要がある。**

### 5.5 投票の設計

**順位型**（確定）。

| | 投票の問い | 落選した論点の扱い |
|---|---|---|
| 選抜型（不採用） | 「今日どれを議論しますか」 | **落選**。今日は否定された |
| **順位型（採用）** | **「どれから始めますか」** | **2番目**。落選が存在しない |

- 30分で1番目しか終わらないのは同じだが、2番目は「落ちた」のではなく「時間が足りなかった」
- **次回の起点論点は、投票で2位だった論点**。正統性を持って引き継がれる
- **票数は表示しない。順位だけ表示する**（P3との整合）

```
❌  ① 12票  ② 3票  ③ 1票
⭕  1番目：①    2番目：②    3番目：③
```

**これは決議ではなくアジェンダの投票。法的拘束力がゼロなので、公式会議に持ち込んでも何も壊さない。**

### 5.6 ラップアップの出力形式

決議ではなく**仕分け**。そのまま台帳のスキーマになる。

| 分類 | 台帳での扱い |
|---|---|
| **決めたこと** | 確定。次回は蒸し返さない |
| **考えること**（継続検討） | 次回の起点論点の候補 |
| **今日触れなかった論点** | 台帳に残る。消えない |

**次回の冒頭は、ここから自動生成される。**
「前回、①は決まりました。②は継続検討、③④は未着手です」——理事が交代していても30秒で引き継がれる。

## 6. 物理構成

```
【入力】主催者のシンプルな機材1台が、部屋の音声を拾う
        参加者の操作はゼロ（ただ喋るだけ）
        ※話者分離はしない

【処理】音声 → 発話単位に分割 → 論点分類 → マップ更新

【出力①】参加者全員のスマホ ＝ 論点ボード（縦ツリー）＋ 投票UI
         ※プロジェクタ不要。同時に「配布装置」でもある

【出力②】主催者の手元（横長画面）＝ 放射状マインドマップ ＋ 介入サジェスト
         主催者が自分の言葉で言う
```

**制約：** 主催者は多くの機材を持ち込めない。シンプルな1台のみ。

### 6.1 実運用のリスク

| | リスク | 影響 |
|---|---|---|
| **通信** | マンション集会室・学校の教室はWi-Fiなしが普通。地下は圏外 | **全滅する** |
| **電池** | 60分間、画面を点けっぱなし。高齢者のスマホは電池が劣化 | 後半で脱落 |
| **スマホ非所持** | 投票権を失う → **「投票で正統性を決める」設計の穴** | 一言で会議が止まる |

スマホ非所持への緩和策は「主催者が代理入力する口」だが、これは
**「主催者が票を操作できる」経路**でもあり、別のリスクを持ち込む。→ 未決。

## 7. 画面設計

### 7.1 可視化①：マインドマップ

**同じデータ、2つの表現。**

| | 画面 | 表現 | 役割 |
|---|---|---|---|
| **主催者** | 横長 | **放射状のマインドマップ** | 全体を俯瞰して選ぶ |
| **参加者** | スマホ縦 | **上から下へのツリー** | 今どこにいるかを確認する |

マインドマップは横に広がる表現であり、スマホ縦とは相性が悪い。放射状をスマホに出すと
文字が読めず、ピンチズームを要求することになり、高齢者のところで脱落する。

### 7.2 エッジにラベルを付ける

線が繋がっているだけでは「前後関係が分かる」にならない。**なぜその枝が生えたか**が要る。

```
【起点】共用自転車を廃止するか
    │
    ├─（コスト面の懸念から）→ 管理費の負担
    │
    └─（利用者への影響として）→ 高齢者の移動手段
```

### 7.3 【実装制約】レイアウトを動かしてはいけない

マインドマップは、新しいノードが増えるたびに再配置すると**全体が動き回る**。
会議中にそれをやると誰も目で追えない。

- **既存ノードの位置は固定し、新しい枝だけを追加する**（append-only レイアウト）
- 一般的なマインドマップ描画ライブラリの既定挙動と逆なので、**自前で押さえる必要がある**

### 7.4 可視化②

可視化①とは別物。

| | 可視化① | 可視化② |
|---|---|---|
| 対象 | 論点**間**の関係（広がりの地図） | 論点**内**の構造（対立軸・合意点） |
| 見せ方 | 論点が3〜5個、木構造で並ぶ | 1論点を深掘りした図 |
| 流用元 | 広聴AI `llm_grouping` | **いどばた `DebateAnalysis`**（axes / agreementPoints / disagreementPoints） |

**可視化②は、いどばた本体の `DebateAnalysis` がほぼそのまま使える。**

## 8. 論点の扱い

### 8.1 論点の粒度

**第1階層で3〜5個**に収める。

根拠が2つ、独立に同じ数字に着地している：

1. **認知の限界。** 人間が同時に把握できる論点は3〜5個。スマホ画面に収まる数とほぼ一致
2. **広聴AIの立方根則。** `lv1 = max(2, min(10, round(N ** (1/3))))`

| 発言数 | 第1階層のクラスタ数 |
|---|---|
| 50件 | 4 |
| 100件 | 5 |
| 150件 | 5 |

会議規模（発言50〜150件）で、自然に4〜5になる。**第2階層は会議では使わない。**

### 8.2 【注意】論点の数を指標にしてはいけない

「論点の数」は**見せるもの**であって、**測るもの**ではない。

「今日は論点が5つ見つかった＝成果」と評価すると、AIは論点を細かく割る方向に最適化される。
「駐輪場の位置」と「駐輪場の料金」を別論点にすれば数が増える。
**粒度を3〜5に収めるルールと真正面から衝突する。**

→ Phase 0 の測定項目に「論点数」は入れない。入れるのは**参加者の認識一致率**。

### 8.3 認知の4点セット（熊平美香）

論点分離の理論的裏付け。

| 層 | 問い | 性質 |
|---|---|---|
| **意見** | どう考えるか | 表に出る。唯一議論されがち |
| **経験** | その背景にある、実際に見聞きした事実 | 検証可能。**事実と価値を分ける鍵** |
| **感情** | その経験に紐づく感情 | 本人しか持っていない |
| **価値観** | そこから見える、大切にしていること | **対立の真の所在** |

例：

| | Aさん（廃止派） | Bさん（存続派） |
|---|---|---|
| 意見 | 廃止すべき | 残すべき |
| 経験 | 放置自転車で通路が塞がれ、救急車が入れなかった | 高齢の親が自転車なしでは買い物に行けない |
| 感情 | 不安・苛立ち | 心配・申し訳なさ |
| 価値観 | **安全**、秩序 | **安全**、生活の継続性 |

**両者とも「安全」と言っているが、指しているものが違う。**
意見だけを突き合わせている限り、この構造は永遠に見えない。

**ただし P2（話者分離を捨てる）により、4点セットは個人に紐づけない。**
「場に、秩序という価値観と、生活の継続性という価値観がある」という形で扱う。
「Aさんの価値観」と言った瞬間、それはAさんへの評価になるため。

### 8.4 論点台帳（組織単位で永続）

会議単位ではなく**組織単位**で論点を保持する。

**理由：マンション管理組合の理事は多くが1年輪番交代。毎年、組織の記憶がゼロリセットされる。**
去年「駐輪場の件は秩序と生活の2つの論点がある」と分かっていても、今年の理事は知らない。
だから毎年、同じ議論を最初からやる。これは「会議が下手」ではなく**組織記憶の欠損**である。

台帳の3つの役割：

1. **組織記憶** — 理事交代で消える記憶を埋める
2. **スイッチングコスト** — 台帳が厚くなるほど次回の価値が上がる。サブスクなしでロックインが効く
3. **選択の正統性の担保** — 「選ばれなかった論点が消えていない」ことが全員に見えている

**台帳は無料で預かり、課金は会議を開く瞬間だけ。** ストレージコストは会議1回の原価に比べて無視できる。

台帳に必要だが未実装のもの：

- 論点の**ライフサイクル**（提起 → 審議中 → 決着 → 再燃）。`SharpQuestion` に状態機械がない
- 会議をまたいだ**同一性判定**。去年の「駐輪場の秩序」と今年の「自転車が邪魔」が同じ論点だと気づく必要がある → 埋め込み検索

## 9. 技術構成

### 9.1 処理の2層構造

| | 処理 | 頻度 | モデル | 原価 |
|---|---|---|---|---|
| **層1** | 発話ごとに「既存論点のどれか／新規か」を判定 | 30分で100回程度 | 小型・高速 | 安い |
| **層2** | 論点構造の再編成（統合・分割・マップ更新） | **層1が「新規」を検出したときだけ**。最低2回 | 上位モデル | 高いが回数が少ない |

「常時LLMを回すから原価が読めない」という問題は、**層を分けることで解消される。**

この構造は広聴AIの `llm_grouping` と**同型**：

```
GroupDiscovery（論点の発見）  → 稀に実行 = 層2 = 可視化①②のタイミング
GroupAssignment（発言の割当） → 頻繁に実行 = 層1 = 発話ごと
```

**この分離は、会議中に何度計算してもマップの形が変わらないことを保証する。**
グループ定義を固定したまま、新しい発言だけ割り当てればよい。**安定性が要件である会議用途に必須。**

### 9.2 外部OSSとの関係

#### いどばた本体（GPL-3.0）

| 資産 | 転用 |
|---|---|
| `DebateAnalysis`（axes / agreementPoints / disagreementPoints） | **可視化②にほぼそのまま使える** |
| `Theme` × `SharpQuestion` × `QuestionLink` | 台帳のデータモデルの原型 |
| Socket.IO によるリアルタイム配信 | 参加者スマホへの配信 |
| `questionVisualReportGenerator` | ラップアップの成果物 |
| **`dailyBatchProcessor`（日次cron）** | **使えない。** リアルタイム化が新規開発の本体 |

#### 広聴AI（kouchou-ai / **AGPL-3.0**）

- リポジトリ：`digitaldemocracy2030/kouchou-ai`
- **使うべきは `hierarchical_clustering` ではなく `llm_grouping`**

| | `hierarchical_clustering` | **`llm_grouping`** |
|---|---|---|
| 方法 | 埋め込み → UMAP → KMeans → 階層化 | **LLMがグループを発見 → 各意見を割り当て** |
| 小N（100件）での安定性 | **不安定**。UMAPは少数データで結果が揺れる | **安定** |

**実装差分：** 広聴AIの階層は `lv1 → lv2`（大分類→小分類）。
会議で必要なのは**起点→派生**（発生の系譜）。**意味が違う。**
`GroupDiscovery` に `parent_group_id` と `relation_label` を出させる拡張が要る。

**不要になるもの：** P3（意見の多寡を見せない）により散布図が不要 → **埋め込み・UMAP・座標計算が全部不要**。

**ライセンス：AGPL-3.0 を受け入れる（確定）。**
GPLv3 と AGPLv3 を結合すると結合物全体が実質 AGPL の条件下に入る。
本プログラムをSaaSとして提供した時点で全ソースの公開義務が生じるが、これは受容する。

> AGPLは普及戦略と整合する。誰でもフォークして自前ホストできることは「デフォルトになる」には有利。
> 管理組合が自前でサーバを立てることは現実には起きないので実害は小さい。
> **堀（moat）はコードではなく、論点台帳の蓄積に置く。**

### 9.3 【推奨】いどばた本体には載せない

| | 理由 |
|---|---|
| いどばたは**日次バッチ前提**の構造 | リアルタイム会議とは設計が逆。既存の制約に縛られる |
| `Theme` / `SharpQuestion` のモデル | 会議用にはズレる。曲げて使うと両方が歪む |
| Railway が**プラン上限に張り付き** | 8vCPU/8GB、Replica 1。相乗りさせると**本体が落ちる** |

→ **別リポジトリ・別アプリで作り、いどばたと広聴AIは「参考にする」に留める。**
統合は、動くものができてから考える。

## 10. 事業設計

### 10.1 顧客と痛み

- 痛みは**全員に薄く分散**しており、所有者がいない
- **犠牲を払っているのは主催者**（理事長・PTA会長など、無報酬のボランティア個人）
- 持ち込むのも**主催者**

### 10.2 課金

| | |
|---|---|
| 方式 | **一回こっきり。単発定額。それがデフォルトになっていること** |
| 条件 | **会議費として処理でき、誰も文句を言われない額** |
| 価格 | ¥500（主催者案）。**私見では会議費の閾値はもっと上（感覚値：¥5,000程度までは議題にならない）** |
| 軸 | **定額必須。** 人数・時間による変動は不可 |

**「会議費で処理する」という条件が、3つを同時に決めている：**

1. **決裁の壁が消える。** 「AIツール代」は新規費目だが、**会議費はすでに予算書にある**。お茶代・コピー代と同列
2. **課金軸が定額に決まる。** 変動すると事前に額が読めず、立て替える主催者が困る
3. **価格の上限が定義される。** 誰も議題にしない額

**実装要件：**

- **領収書・請求書の発行が必須**（組合名義）
- **アプリ内課金（App Store / Google Play）は使えない。** 組合宛の領収書が出せない → **Web決済一択**
- **事前契約なしで、当日その場で決済できること**（会議費の実務は「立て替えて後で精算」）
- アカウント登録に5分かかると開始前に脱落する

### 10.3 獲得：営業ができない

**単発課金は、獲得コストが1回の粗利を超えた瞬間に永久に回収不能になる。**
サブスクなら初回赤字を翌年以降で回収できるが、単発はその1回で黒字にならなければ終わり。

> **「営業しない」は選択ではなく、この課金設計が強制する制約。**

したがって獲得経路は事実上ひとつしかない。そしてそれは設計の中に既にある。

```
1回の会議で、15人が自分のスマホで製品を体験する
    ↓
その15人の中に、別の会議の主催者が混じっている
    （管理組合の理事はPTA役員でもあり、町内会員でもあり、サークルの幹事でもある）
    ↓
「うちの会でも使いたい」
    ↓
次の主催者になる
```

**参加者のスマホを使う構成は、UI上の制約回避ではなく、獲得チャネルそのもの。**
プロジェクタ投影なら「1画面を全員で見た」で終わるが、スマホなら15人の手元に製品が入る。

### 10.4 市場規模（**すべて公開統計の記憶からの概算。要検証**）

| 前提（感覚値） | 値 |
|---|---|
| 全国の分譲マンション管理組合 | 約12〜13万組合 |
| 小中学校のPTA | 約3万校弱 |
| 年間の対象会議回数 | 4回 |

**単発課金のみ、浸透率100%で：**

- 管理組合：12万 × 4回 × ¥500 ＝ **年2.4億円**
- PTA：3万 × 4回 × ¥500 ＝ **年0.6億円**
- 合計 **約3億円**

「日本中の管理組合とPTAが**全部**使って年3億」という意味。浸透率10%なら年3,000万円。

**→ 単発課金だけでは事業規模が小さい。サブスクは本体であり、オプションではない。**

### 10.5 サブスク（Phase 0 の後）

**100会議を終えた後にサブスクを始める。**

**未解決の宿題：** サブスクは会議費で処理できない。

| | 処理 | 決裁 |
|---|---|---|
| 単発 | **会議費**。領収書1枚 | **ゼロ** |
| **サブスク** | 予算計上・年契約 | **総会決議または予算承認** |

しかも判断するのは、去年の良さを知らない新理事（1年輪番交代）。

選択肢（**今は決めない。Phase 0 のデータで決める**）：

- **(α)** サブスクを名乗らず「年間分の会議費前払い」として会議費の枠内に留め、決裁を発生させない
- **(β)** 契約主体を組合から外す。管理会社・PTA協議会などが複数組合分をまとめて契約（＝B2B）

→ **Phase 0 の測定項目に変換する：** 「続けたい」と言った組織に、**どう払うつもりかを聞く。**

### 10.6 撤退基準

> **再利用がなければ撤退。**

指標の選択は正しい。再利用率は本製品にとって最も本質的な数字であり、
**撤退基準とサブスク開始基準が同じ指標になっている**点で整合している。

**未決（2点）：**

1. **線が引かれていない。** 「なければ」は0%か、20%か、50%か。数字がないと判断時に揉める
2. **観測に時間がかかることが計算に入っていない**

| 会議体 | 次回まで |
|---|---|
| 管理組合の理事会 | **約1ヶ月** |
| 管理組合の総会 | **約1年** |
| PTAの役員会 | 1〜2ヶ月 |
| 非公式の集まり | 不定期 |

> **Phase 0 は、最短でも6ヶ月。現実的には1年。**

100会議を3ヶ月で回しても、再利用が分かるのはさらに数ヶ月先。
**理事会（月1回）を最初に狙えば観測が最短になる。総会（年1回）から入ると撤退判断が1年遅れる。**

### 10.7 【整合が取れていない箇所】

| | ずれ |
|---|---|
| 1 | **「拡散は悪くない」× 単発課金** — 残った論点は台帳に積むが、**次回が開かれる保証がない** |
| 2 | **営業ゼロ × デフォルト化** — K値が**未測定**。1.0を割ると自己増殖しない |
| 3 | **無報酬の個人 × 会議費** — 立て替えて精算するUXが未設計 |
| 4 | **「宿題ゼロ」× 公式会議** — 下記参照 |

#### 4 の詳細：公式会議では「宿題ゼロ」は成立しない

管理組合の総会・理事会の議事録は**法定文書**（区分所有法で作成・保管義務）。
AIが生成したものをそのまま正式議事録にはできない。

| | AIのまとめ | 主催者の宿題 |
|---|---|---|
| **非公式**の会議 | そのまま記録になる | **ゼロ** |
| **公式**の会議 | 議事録の**ドラフト**にしかならない | **残る** |

公式会議で言えるのは「**宿題が10分の1になる**」まで。
**「両方に適用する」なら、売り文句は公式側の水準に合わせるべき。**
非公式でしか成立しない約束を掲げると、公式で使った人が裏切られる。

## 11. Phase 0：測定設計

**新規事業では「数字を出すこと」より「測定する設計を作ること」が優先。実測値はまだ1つもない。**

### 11.1 対象

**硬軟・大小を交えた、いろいろな場で100会議。**

| 分類 | 定義 | 投票の意味 | スマホ非所持 | ¥3,000 |
|---|---|---|---|---|
| **硬**（公式） | 利害が絡み、金が動き、決議が要る | **政治になる。正統性が問われる** | **致命的** | 安い |
| **軟**（非公式） | 決議不要、探索的 | 遊び。誰も揉めない | 問題にならない | **高い** |

**条件：無作為に散らすのではなく、軸を持って散らすこと。**
10種類 × 10回では各セグメント10サンプルとなり、統計的に何も言えない。

**分散させる軸（優先順）：**

| 軸 | 測りたいこと | 不確実性 |
|---|---|---|
| **参加者の年齢層** | **スマホ投票が成立するか** | **最大。ここが崩れると設計全体が崩れる** |
| 利害対立の強さ（硬軟） | 投票が政治になるか遊びになるか | 大 |
| 決議の要否 | 「決めること／考えること」の仕分けが機能するか | 中 |
| 参加人数（5／15／30人） | 論点が3〜5に収まるか | 中 |
| 組織の継続性（1年交代／固定） | 台帳が効くか | 大（1回では測れない） |

### 11.2 測定項目（優先順）

| # | 項目 | なぜ |
|---|---|---|
| **1** | **K値**：参加者15人中、何人が「自分の会議でも使いたい」と答えるか | **事業の成否そのもの。**1.0超で自己増殖、0.1なら永遠にデフォルトにならない |
| **2** | 可視化した直後、議論が**再開したか／凍りついたか** | **製品仮説（3.2）の生死** |
| **3** | **再利用率**：同じ組織が2回目を開いたか | **撤退基準 兼 サブスク開始基準** |
| **4** | スマホで投票できない参加者が何人いるか | 正統性の穴の実寸 |
| **5** | 会議費として黙って通る**上限額**（会計担当に3人聞けば分かる） | 価格設計 |
| **6** | **1会議あたりの実測原価**（音声認識＋LLM） | 粗利が残るかの判定 |
| **7** | 終了時、参加者が挙げる「今日の論点」の**一致率** | 可視化の成否 |
| **8** | 「続けたい」と言った組織が、**どう払うつもりか** | α／β の判断材料 |

**測定項目に入れないもの：論点の数**（8.2 参照）。

### 11.3 原価の分解（**不確実性の所在**）

| 費目 | 不確実性 | 備考 |
|---|---|---|
| A. 音声認識（50分。開始遅れの10分は不要） | 低 | 公開価格で計算可能 |
| B. 話者分離 | — | **P2により不要になった** |
| C. 発話ごとの論点分類（層1、100〜200回） | 中 | モデル選択次第で10倍変わる |
| D. 論点構造の再編成（層2） | **最高** | **発火回数が原価を決める** |
| E. マップ生成・更新 | 低 | |

**現時点で「¥500で粗利が残るか」は誰にも言えない。** D の実測が必要。

## 12. プロトタイプ計画

| | 段階 | 作るもの | 検証できること | 期間（感覚値） |
|---|---|---|---|---|
| **L0** | **手動再現** | **コード0行** | 論点抽出の精度、マップの有用性、凍りつくか | **1週間** |
| **L1** | Wizard of Oz | マップ表示＋投票の画面だけ。中身は人力 | リアルタイム体験、投票、K値 | 2〜3週間 |
| **L2** | 半自動 | 音声認識・論点抽出は自動。タイミングだけ人間 | 精度、**実測原価** | 1〜2ヶ月 |
| **L3** | フル自動 | 製品 | — | — |

### L0：最も危険な仮説を、コードなしで潰す

> **AIが、実際の会議の会話から、意味のある論点マップを出せるのか。**

ここが成り立たなければ、投票UIもマインドマップ描画も台帳も全部無駄になる。

```
1. 実際の会議を1本、録音する（スマホで十分）
   ↓
2. 文字起こしする（話者分離は不要 ← P2で捨てた）
   ↓
3. LLMに投げて、論点マップを作らせる
   ↓
4. その会議の参加者に見せて、聞く
```

参加者に聞くことは3つだけ：

- **「これ、当たっていますか」** → 論点抽出の精度
- **「これが会議の途中で出ていたら、議論は変わりましたか」** → 製品仮説そのもの
- **「議論は活発になりましたか、それとも空気が悪くなりましたか」** → **凍りつくリスク（3.2）**

### L1：Phase 0 の100会議の主力

**100会議を全自動でやる必要はない。**

会場の隅（または別室）でオペレータがPCを見ながら文字起こしを読み、論点マップを作って
参加者のスマホに送る。**中身は人力、参加者からは製品に見える。**

作るのは2つだけ：

| | 内容 | 規模 |
|---|---|---|
| 参加者画面 | QRで参加 → マップ（縦ツリー）→ 順位投票 | React + Vercel。小さい |
| オペレータ画面 | 文字起こしを読み、マップを作って送信 | 管理画面1枚 |

**K値も、凍りつくかも、投票が機能するかも、全部測れる。**
測れないのは「自動化の精度」と「実測原価」だけ（L2で測る）。

**L0／L1 では広聴AIのコードを持ってくる必要はない。プロンプト1本で足りる。**
AGPLの継承も、コードを実際に組み込む段階（L2以降）まで発生しない。

## 14. 確定事項サマリ

- 成功＝**結論ではなく論点の可視化**。拡散は悪くない。持ち越しは正当な着地
- **AIは決めない。現在地だけを言う**
- **話者分離を捨てる。**「誰が」ではなく「何を」
- **意見の多寡は見せない。論点の数だけ見せる**
- 60分 ＝ 開始遅れ10 ／ 課題共有10 ／ **コア30** ／ ラップアップ10
- 区切りは1回。**時計ではなく「投票」という人間の行為**で起きる
- **投票は順位型。「どれから始めるか」。落選という概念を作らない。票数は隠す**
- 入力＝主催者の機材1台の音声。**参加者の操作は投票のタップのみ**
- 出力＝参加者スマホ（縦ツリー）＋主催者の横長画面（放射状マインドマップ）
- **マップのレイアウトは動かさない**（append-only）
- 論点の粒度＝**第1階層で3〜5個**
- **論点台帳は組織単位で永続。無料で預かる**
- 課金＝**一回こっきりの定額。会議費として処理でき、誰も文句を言われない額**
- **営業はしない（できない）。**獲得は参加者のスマホ経由の伝播のみ
- 100会議の後に**サブスクを始める**
- **再利用がなければ撤退**
- **AGPL-3.0 を受け入れる**
- **公式・非公式の両方に適用できることが要件**
- **いどばた本体には載せず、別アプリとして作る**

````
会議の文字起こし（話者は特定されていません）。

# やること
1. 発言を読み、議論されている「論点」を抽出する
2. 論点どうしの親子関係（どの論点から、どの論点が派生したか）を判定する
3. 各論点について、場に出ている「意見／経験／感情／価値観」を整理する

# 厳守するルール
- **誰が言ったかは一切扱わない。** 「Aさんは」のような書き方をしない
- **何人が言ったかも書かない。** 論点はすべて同じ重みで扱う
- **第1階層の論点は3〜5個に収める。** 多すぎる場合は統合する
- 階層は最大2階層まで
- 「私は反対だ」のような立場の表明は、それ自体を論点にしない。背後にある論点を探す
- **事実確認で済む話（経験層）と、価値判断が必要な話（価値観層）を分ける**
- 論点の名前は、賛否のどちらにも偏らない中立な表現にする
- 推測で埋めない。場に出ていないことは「言及なし」と書く

# 出力形式（JSON）
{
  "starting_issue": "主催者が最初に提示した論点",
  "issues": [
    {
      "id": "i1",
      "parent_id": null,
      "relation_label": null,
      "label": "論点の名前（20字以内・中立）",
      "opinions": ["場に出ている意見"],
      "experiences": ["語られた事実・経験（検証可能なもの）"],
      "emotions": ["場に現れた感情"],
      "values": ["背後にある価値観"],
      "fact_or_value": "fact | value | both",
      "repeat_count": 2
    },
    {
      "id": "i2",
      "parent_id": "i1",
      "relation_label": "コスト面の懸念から",
      "...": "..."
    }
  ],
  "drift_notes": [
    "論点がズレた箇所の指摘（例：『共用自転車の廃止』の議論が『高齢者の安全性』に移っています）"
  ]
}
````

**検証の観点：** 出力された `issues` が会議の実感と合っているか。`drift_notes` が的を射ているか。
`repeat_count` が高い論点は「この論点は3回目です」の介入に使う。
